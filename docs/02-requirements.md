# 在庫・出荷オーダー管理システム 要件定義書

## 1. システム概要

食品・日用品を取り扱う総合物流会社を想定する。

複数の法人荷主から商品を預かり、1つの物流センターで在庫を管理する。
物流会社の担当者が荷主から受けた出荷依頼をシステムへ登録し、在庫確認・在庫引当を行ったうえで後続の出荷工程へ引き渡す。

本システムの対象は以下とする。

```text
荷主から出荷依頼を受領
        ↓
物流会社の担当者が登録
        ↓
出荷オーダー作成
        ↓
在庫確認
        ↓
在庫引当
        ↓
後続の出荷工程へ引き渡し
```

---

## 2. システム前提

- Organizationは1社固定
- Warehouseは1物流センター固定
- 複数の法人荷主を管理する
- 荷主自身はシステムを操作しない
- 出荷依頼の受領方法（電話、メール、FAX、EDI等）はシステム対象外
- 商品数量は整数のみ扱う
- 商品単位は初期版では「個」固定
- 在庫は荷主単位で分離する

---

## 3. 利用者・権限

### 3.1 OPERATOR

物流会社の業務担当者。

- 出荷オーダー一覧閲覧
- 出荷オーダー登録
- 出荷オーダー詳細閲覧
- 出荷オーダーキャンセル
- 後続工程への引き渡し
- 在庫一覧閲覧

### 3.2 ADMIN

OPERATORの権限に加えて以下を行える。

- 実在庫の調整

### 3.3 認証・認可

初期版ではDemo Authenticationを使用する。

ログイン画面に以下を配置する。

- 担当者としてログイン
- 管理者としてログイン

Demo OPERATOR / Demo ADMINはSeedデータとして用意する。

本認証は実装しないが、Authorizationはバックエンド側で実装する。
OPERATORによる在庫調整APIの実行は拒否する。

## 4. 出荷オーダー

### 4.1 基本仕様

- 1つのOrderに複数のOrderItemを持てる
- 荷主を指定する
- 出荷先名称を保持する
- 出荷先住所を保持する
- 希望出荷日を保持する
- 商品と数量を複数指定できる
- 出荷先はマスタ化せずOrderへ直接保持する

### 4.2 登録処理

出荷オーダー登録時に在庫引当を行う。

```text
入力検証
  ↓
荷主・商品確認
  ↓
全商品の引当可能在庫確認
  ↓
Order作成
  ↓
OrderItem作成
  ↓
Allocation作成
  ↓
Inventory更新
```

1商品でも必要数量を引き当てられない場合、オーダー全体を失敗させる。

部分引当は行わない。

### 4.3 ステータス

以下の状態を使用する。

- `ALLOCATED`
- `HANDED_OVER`
- `CANCELLED`

許可する状態遷移：

```text
ALLOCATED → HANDED_OVER
ALLOCATED → CANCELLED
```

禁止する状態遷移：

```text
HANDED_OVER → CANCELLED
```

### 4.4 キャンセル

`ALLOCATED`状態のみキャンセル可能とする。

キャンセル時は対象Orderに紐づくAllocationを解除し、引当済数量を戻す。

Orderの状態変更とAllocation解除は同一トランザクションで処理する。

## 5. 在庫

### 5.1 Inventory

Inventoryは以下を保持する。

- `onHandQuantity`：実在庫
- `allocatedQuantity`：引当済在庫

引当可能在庫は保存せず、以下で算出する。

```text
availableQuantity = onHandQuantity - allocatedQuantity
```

常に以下を満たすこと。

```text
onHandQuantity >= 0
allocatedQuantity >= 0
allocatedQuantity <= onHandQuantity
```

### 5.2 在庫引当

Allocationを独立Entityとして保存する。

Allocationから以下を追跡可能とする。

- 対象OrderItem
- 対象Inventory
- 引当数量

在庫引当時は`onHandQuantity`を減らさず、`allocatedQuantity`を増加させる。

### 5.3 後続工程への引き渡し

`HANDED_OVER`へ変更してもAllocationは維持する。

実在庫の減算およびAllocationの解消は、出荷完了処理で行う想定とし、初期版では扱わない。

### 5.4 在庫調整

ADMINのみ実在庫を調整できる。

OPERATORは在庫を閲覧できるが変更できない。

## 7. 入力・エラー

### 7.1 入力検証

システム境界で以下を検証する。

- 必須項目
- データ型
- ID形式
- enum
- 配列構造
- 数量が1以上の整数であること

在庫不足や状態遷移可否は業務ルールとして判定する。

### 7.2 エラー

最低限、以下を区別する。

- 400：入力不正
- 403：権限不足
- 404：対象データ不存在
- 409：在庫不足、競合等の業務エラー
- 500：予期しないシステムエラー

在庫不足時は対象商品を特定できるメッセージを返す。

## 8. 非機能要件

### 8.1 データ整合性

同一在庫に対して複数の出荷オーダーが同時に登録されても、実在庫を超える在庫引当を発生させない。

```text
allocatedQuantity <= onHandQuantity
```

を常に満たすこと。

### 8.2 トランザクション

出荷オーダー登録では、以下を一つの業務単位として扱う。

- Order作成
- OrderItem作成
- Allocation作成
- Inventory更新

1つでも失敗した場合、すべて変更前の状態へ戻す。

### 8.3 同時実行検証

同一商品に対して同時100リクエストを実行する。

基準データ：

```text
onHandQuantity = 100
1オーダーあたりの引当数量 = 10
```

期待結果：

- 成功オーダーは最大10件
- 実在庫超過0件
- `allocatedQuantity <= 100`
- `availableQuantity >= 0`

改善前後の結果を数値で記録する。

### 8.4 性能

初期版では具体的な応答時間目標を設定しない。

大量データ投入によるDB性能検証およびフロントエンド性能計測は後続検証とする。

### 8.5 再現性

ローカル環境でシステムを起動できること。

Seedデータとして最低限以下を用意する。

- Organization × 1
- Warehouse × 1
- Demo OPERATOR
- Demo ADMIN
- 複数の荷主
- 複数の商品
- 在庫データ

環境構築手順はREADMEへ記載する。
