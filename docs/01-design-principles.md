# 設計原則

## 1. 基本方針

本システムは、以下の構成を基本とする。

- プレゼンテーション層
- アプリケーション層
- データソース層
- ドメインモデル

業務ルールをフレームワークや画面、データベースの都合に埋め込まず、変更理由ごとに責務を分離する。

設計上の判断では、以下を優先する。

1. 業務ルールがコードから読み取れること
2. 変更の影響範囲が限定されること
3. 不正な状態を作りにくいこと
4. 同じ業務ルールを複数箇所に重複させないこと
5. 実装の都合より業務上の意味を優先すること

---

## 2. レイヤー構成

### 2.1 プレゼンテーション層

HTTP、画面、入力、出力など、外部との境界を担当する。

主な責務：

- HTTPリクエストの受け付け
- リクエスト形式の検証
- 認証済みユーザー情報の受け渡し
- アプリケーション層の呼び出し
- HTTPレスポンスへの変換
- 画面表示とユーザー操作

プレゼンテーション層には業務ルールを書かない。

Controller、Route、React Componentから直接データベースを操作しない。

---

### 2.2 アプリケーション層

ユースケースの進行を担当する。

主な責務：

- ユースケース単位の処理
- ドメインモデルの呼び出し
- 複数のドメインオブジェクトやRepositoryの調整
- トランザクション境界の制御
- 外部サービス呼び出しの調整

アプリケーション層は「何を行うか」を表現し、個別の業務ルールそのものは可能な限りドメインモデルへ置く。

例：

- 注文を登録する
- 在庫を引き当てる
- 注文をキャンセルする

---

### 2.3 データソース層

データベースや外部サービスとの具体的な接続を担当する。

主な責務：

- PostgreSQLへのアクセス
- Prismaによる永続化
- Repositoryの実装
- 外部APIとの通信
- データ取得・保存方法の具体化

データソース層の都合をドメインモデルへ漏らさない。

Prisma固有の型やデータベース固有の表現を、必要以上に上位層へ持ち込まない。

---

### 2.4 ドメインモデル

業務上の概念、状態、制約、判断を表現する。

主な責務：

- 業務上意味のある値の表現
- 状態遷移
- 業務ルール
- 不変条件
- 業務上許可される操作の判定

例：

- 在庫数は0未満にならない
- 出荷済み注文を未確定状態へ戻せない
- 注文数量は1以上である
- 引当可能数を超える在庫引当を行えない

ドメインモデルは、Next.js、NestJS、Prisma、PostgreSQLなどの具体的な技術へ依存させない。

---

## 3. 依存関係

依存方向は原則として以下とする。

```text
Presentation
    ↓
Application
    ↓
Domain

Data Source
    ↑
Application
```

ドメインモデルは他のレイヤーへ依存しない。

プレゼンテーション層からデータソース層を直接呼び出さない。

データアクセスの具体実装はデータソース層へ閉じ込め、アプリケーション層からはRepository等の明確な境界を通して利用する。

---

## 4. 業務ルールを一箇所に集約する

同じ判断をController、Service、React Component、Repositoryなど複数箇所へ重複させない。

例えば「在庫を引き当てられるか」という判断は、画面側とAPI側で別々に実装しない。

画面側で操作を無効化する場合でも、最終的な業務ルールの保証はサーバー側で行う。

```text
画面上の制御
    +
サーバー側の業務ルール
```

という役割分担とし、画面上の制御だけを正しさの根拠にしない。

---

## 5. 不正な状態を作りにくい設計にする

単なるプリミティブ型だけで業務上の制約を表現しない。

必要に応じて、業務上意味のある値を専用の型やオブジェクトとして表現する。

対象例：

- OrderQuantity
- StockQuantity
- OrderStatus
- Money
- CustomerId
- ProductId

すべてを専用クラスにすることを目的とせず、業務ルールを守る価値がある箇所に限定して導入する。

---

## 6. 状態遷移を明示する

ステータスは単なる文字列として自由に更新させない。

許可される状態遷移を明示し、不正な遷移を拒否する。

例：

```text
PENDING
  ↓
CONFIRMED
  ↓
ALLOCATED
  ↓
SHIPPED
  ↓
COMPLETED
```

キャンセル可能な状態や、在庫を戻す必要がある状態についても業務ルールとして定義する。

状態変更処理を複数箇所へ分散させない。

---

## 7. 入力検証と業務検証を分離する

外部から受け取る値は、システム境界で検証する。

Zod等による検証は、主に以下を対象とする。

- 必須項目
- 型
- 文字列形式
- 数値形式
- 列挙値
- リクエスト構造

一方、以下は業務ルールとして扱う。

- 在庫が足りているか
- 注文をキャンセル可能か
- 出荷済み注文を変更可能か
- 指定数量を引き当て可能か

形式上正しい入力と、業務上許可される操作を混同しない。

---

## 8. トランザクション境界は業務単位で決める

データベース操作単位ではなく、業務として一貫性を保証する必要がある範囲をトランザクション境界とする。

例えば受注処理では、

```text
注文作成
+
在庫確認
+
在庫引当
```

が一つの業務単位になる場合、途中状態を残さない。

同時実行時にも業務上の不変条件が壊れないことを優先する。

特に在庫引当では、以下を保証する。

- 在庫数を超えて引き当てない
- 同時注文によって在庫が負数にならない
- 失敗時に注文と在庫が不整合にならない

---

## 9. データベース制約も正しさの一部として利用する

アプリケーションコードだけで整合性を保証しようとしない。

必要に応じて以下を利用する。

- NOT NULL
- UNIQUE
- FOREIGN KEY
- CHECK
- INDEX

業務上絶対に破ってはいけない条件については、アプリケーション側の検証とデータベース側の制約を組み合わせる。

---

## 10. 名前で業務上の意図を表現する

変数名、関数名、クラス名から処理の目的が読み取れることを優先する。

避ける例：

```ts
if (s >= q) {
  // ...
}
```

意図を表す例：

```ts
if (stock.canAllocate(orderQuantity)) {
  // ...
}
```

実装方法ではなく、業務上何を行っているかが名前から分かるようにする。

---

## 11. 関数とクラスの責務を小さく保つ

一つの関数やクラスが複数の変更理由を持たないようにする。

特に以下が一つの処理へ混在しないよう注意する。

- HTTP処理
- 入力検証
- 業務判断
- データベースアクセス
- 外部API通信
- レスポンス変換

処理を短くすること自体を目的とせず、責務の境界が明確であることを優先する。

---

## 12. コメントではなくコードで意図を表現する

処理内容を説明するコメントを増やす前に、名前や構造で意図を表現できないか検討する。

コメントは主に以下の場合に使用する。

- なぜこの設計を選んだか
- なぜ一見不自然な処理が必要か
- 外部仕様による制約
- 性能・整合性上の理由

コードを読めば分かる処理内容を、そのままコメントで繰り返さない。

---

## 13. フロントエンドではサーバー状態とUI状態を分ける

サーバーから取得するデータと、画面内部だけで使用する状態を区別する。

TanStack Query等が扱う対象：

- 注文一覧
- 在庫一覧
- 商品情報
- API取得結果
- Mutation後の再取得・キャッシュ更新

Reactのローカルstateが扱う対象：

- モーダル開閉
- 入力途中のUI状態
- タブ選択
- 一時的な表示状態

サーバー状態を不必要に複数のReact stateへ複製しない。

---

## 14. フロントエンドの最適化は計測後に行う

`memo`、`useMemo`、`useCallback`等を最初から機械的に使用しない。

再レンダリングや処理時間を計測し、問題が確認できた箇所へ限定して最適化する。

最適化では、変更前後を数値で比較する。

---

## 15. フレームワーク固有処理を境界に閉じ込める

Next.js、NestJS、Prismaなどのフレームワーク固有コードを業務ロジックへ広げない。

特に以下を避ける。

- DomainがPrisma Modelへ依存する
- DomainがHTTP Request / Responseを扱う
- ApplicationがReactやNext.jsのAPIへ依存する
- 業務判断をNestJS Controllerへ直接記述する

フレームワーク変更時に業務ルールまで書き換える必要がない構造を目指す。

---

## 16. 例外とエラーを区別する

エラーは少なくとも以下を区別する。

- 入力形式エラー
- 認証・認可エラー
- 業務ルール違反
- 対象データ不存在
- 競合
- 外部サービス障害
- システム内部エラー

内部例外をそのままクライアントへ返さず、プレゼンテーション層で適切なHTTPレスポンスへ変換する。

---

## 17. 変更可能性を予測しすぎない

将来必要になるかもしれないという理由だけで抽象化を増やさない。

現在確認できている業務ルールと変更理由を基準に境界を作る。

ただし、以下については初期段階から分離する。

- 業務ルールとHTTP
- 業務ルールとDBアクセス
- 入力検証と業務検証
- サーバー状態とUI状態

必要性が確認できてから抽象化を追加する。

---

## 18. 設計判断は制約と理由を残す

重要な設計判断では、採用した方式だけでなく以下を記録する。

- どの制約があったか
- どの案を検討したか
- なぜ採用したか
- 何を犠牲にしたか
- 将来どの条件で見直すか

設計判断を「好み」で説明せず、業務要件、整合性、性能、変更容易性、運用コスト等の制約に結びつける。

---

## 19. テストは業務ルールを中心に置く

テスト対象は実装詳細ではなく、外部から観測できる振る舞いと業務ルールを優先する。

特に以下を重点的に検証する。

- 在庫不足時に注文できない
- 同時注文でも在庫超過しない
- 不正な状態遷移を拒否する
- キャンセル時に必要な在庫が戻る
- トランザクション失敗時に中途半端な状態を残さない

単体テストだけでなく、DBを含む統合テストおよび同時実行テストを行う。

---

## 20. 設計原則の優先順位

原則同士が競合した場合は、以下の順で判断する。

1. データ整合性と業務上の正しさ
2. セキュリティ
3. 業務ルールの明確さ
4. 変更容易性
5. 可読性
6. 性能
7. 実装量の少なさ

ただし、明示された性能要件がある場合は、その制約を満たすために設計を見直す。
